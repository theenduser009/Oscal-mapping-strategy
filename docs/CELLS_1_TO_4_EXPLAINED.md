# Cells One through Four explained

Source version: `08ab607cc288d868549c6fb62aa945d51c55f017`. This walkthrough describes the maintained files in `notebooks/cells`; all four were compared with that GitHub version. Line numbers are one-based and include comments and blank lines.

This is a source-ordered walkthrough of every function and executable configuration block, with additional breakdowns for the larger functions. It is not a prose annotation of every individual line. Open a line link when explaining the corresponding code. Blank lines, comments and closing delimiters belong to their surrounding block.

The boundary is simple: Cell One chooses deployment settings; Cell Two reads inputs; Cell Three compiles approved metadata; Cell Four provides reusable transformations and object builders. Cell Five calls those builders; Cells Six and Seven validate and load the graph. No DIM or FACT target rows are written by Cells One through Four. Cell Two does create session-local temporary snapshots.

Counts and accepted live runs belong in [Current Status](CURRENT_STATUS.md). This document explains what the code does, not whether a particular Snowflake run succeeded.

### Behaviors worth explaining plainly

- Source absence and source null are different. Missing keys use the skip sentinel. Explicit nulls survive only where the CSV null policy or existing AR observation option permits them; null does not satisfy a required value.
- `timestamp` currently validates nonblank text only. It is not a general timestamp parser or timezone normalizer. `date` is the separately validated calendar-date transform.
- Current SSP properties use source-field-plus-value identity; current SAP properties and AR observations use field identity. A changed SSP property value changes its graph identity; the loader's obsolete-row check can then block the load. Do not promise automatic in-place updates for that case.
- A named property may be its own DIM element or may be embedded inside another element's JSON. AR observation properties are embedded; three element types therefore do not mean only three mapped fields.
- Preserved JSON nulls meet the warehouse-preservation requirement. They do not establish conformity with OSCAL property string requirements. The mapper intentionally reports mapped scope rather than a fully validated OSCAL document.
